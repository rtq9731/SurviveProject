# 번역 체계

이 문서 하나만 읽고 다음 문자열 이관을 이어갈 수 있어야 한다.

---

## 0. 왜 자체 CSV 층인가

기성품을 먼저 조사했다.

- **Unity Localization 공식 패키지** — 개념(String Table Collection = 카테고리, Entry Name = 키)은
  우리 요구와 잘 맞는다. 그런데 **Addressables가 하드 의존**으로 딸려 오고 이 프로젝트에는
  Addressables가 전혀 없다. 더 큰 문제는, 그 패키지의 진짜 가치인
  "프리팹의 TMP 컴포넌트에 `LocalizeStringEvent`를 붙이는" 워크플로를 **이 프로젝트가 쓸 수 없다**는 것이다 —
  UI를 전부 코드에서 `GameObject`로 조립하기 때문에 붙일 프리팹이 없다.
- **I2 Localization** — 유지보수가 멎은 것으로 보여 제외.
- **실측 규모** — 코드 안 한글 문자열 약 214개(주석·인스펙터 속성·테스트 제외),
  데이터 에셋 텍스트 필드 101개(displayName 71 / description 23 / hint 7), AI 대사 에셋 5개.
  합쳐 약 320개. 얇은 층 하나로 충분한 크기다.

그래서 **CSV 한 장 + 동기 조회 API + EditMode 게이트**로 갔다.
나중에 Unity Localization으로 갈아탈 수 있게 열 구조를 그쪽과 맞춰 두었다(5절).

## 1. 파일과 형식

**위치**: `SurviveProject/Assets/Resources/Localization/strings.csv`

`Resources` 아래에 둔 이유는 셋을 한꺼번에 만족해야 하기 때문이다 —
게임이 뜨는 **첫 프레임 전에**, **씬과 무관하게**, **동기로** 읽혀야 한다.
Addressables 없이 그것이 되는 것은 Resources뿐이다.
읽는 자리는 `Assets/02.Scripts/Localization/LocalizationBootstrap.cs` 하나뿐이므로,
나중에 갈아탈 때 고칠 파일도 그 하나다.

**CSV가 진실의 원천이다.** 에디터 창에서 편집해 내보내는 방향이 아니다.
사람이 이 파일을 고치면 그것이 곧 게임에 반영된다. git diff가 되고,
번역가에게 그대로 보낼 수 있다.

```csv
Category,Key,ko,en,Comment
UI,craft_empty,아직 아는 제작법이 없다,Nothing you know how to craft yet,
UI,ingredient_entry,{0} {1}/{2},{1}/{2} {0},{0}=재료 이름 {1}=가진 수 {2}=드는 수
Item,mushroom_wood.name,버섯 목재,
```

- 첫 줄이 헤더다. 첫 칸은 반드시 `Category`, 둘째 칸은 반드시 `Key`, 그 뒤가 로케일 열이다.
- **`ko` 칸은 절대 비우지 않는다.** 비면 EditMode 게이트가 실패한다.
- 다른 로케일 칸은 비워도 된다. 비면 `ko`로 폴백한다.
  (**빈 칸은 표에 담지 않는다** — 담으면 화면이 비고 폴백이 돌 자리가 사라진다.)
- **뒤쪽 칸은 모자라도 된다.** 위 예의 `Item` 줄처럼 `Comment`까지 안 적어도 문제로 적지 않는다.
  반대로 칸이 **남으면** 문제다 — 거의 언제나 값 안의 쉼표를 따옴표로 감싸지 않은 것이고,
  그대로 두면 값이 잘려 나간다.

### `Comment` 열 — 번역가에게 `{0}`이 무엇인지 알려 주는 자리

**로케일 열이 아니다.** 이름이 `Comment`인 열 하나만 특별 취급한다.

이 층의 요점은 번역가가 `{0} {1} {2}`의 순서를 마음대로 바꾸는 것인데,
`{0}`만 보고는 무엇이 들어가는지 알 수 없어 **정작 바꾸지 못한다.**
어순을 바꾸라고 만든 규칙인데 못 바꾸면 헛일이므로, 설명을 표 안에 둔다.

- 규약은 `{0}=제작물 이름 {1}=재료 목록` 꼴이다.
  게이트가 **자리표마다 `{n}=`이 있는지** 본다 — 하나만 적고 넘어갈 수 없다.
- `#` 주석 줄이 아니라 열로 둔 이유는 둘이다. 주석 줄은 키에 붙어 있지 않아
  기계가 "이 값의 설명"으로 읽을 수 없고, Unity Localization으로 내보낼 때 사라진다.
  (그쪽에도 `Shared Comments` 열이 있어 그대로 옮겨 간다.)
- **자리가 맨 끝인 이유**: 새 언어를 더할 때 "헤더 끝에 열을 붙인다"(8절)가
  깨지지 않아야 하고, 옛 꼴(`Category,Key,ko,en`)로 적은 줄의 값이 한 칸씩 밀려
  엉뚱한 칸에 들어가는 일이 없어야 한다. 새 로케일 열은 **`Comment` 앞에** 끼운다.

### 파서 규칙 (RFC 4180 + 두 가지)

`Assets/02.Scripts/Domain/Localization/Csv.cs`. 직접 썼다 — 필요한 것은 아래뿐이다.

| 경우 | 쓰는 법 |
|---|---|
| 값에 쉼표 | `UI,k,"재료가 없다, 아직은"` — **한국어에 쉼표는 흔하다** |
| 값에 따옴표 | `UI,k,"그는 ""안 된다""고 했다"` |
| 값에 줄바꿈 | 따옴표로 감싸면 그 안의 줄바꿈은 값의 일부다 |
| 앞뒤 공백 보존 | 따옴표로 감싼다. 감싸지 않아도 파서는 값을 trim하지 않는다 |
| CRLF / LF | 섞여도 된다 |
| UTF-8 BOM | 앞머리 BOM은 무시한다 (엑셀이 저장하면 붙는다) |

RFC에서 벗어난 두 가지 — 둘 다 사람이 표를 구역별로 나눠 읽으라고 허용했다.

- **빈 줄**은 레코드로 세지 않는다.
- **`#`로 시작하는 줄**은 주석이다. (Unity Localization으로 내보낼 때는 이 줄들이 사라진다.)

값 안의 `#`는 영향이 없다. 줄 **첫 글자**만 본다.

## 2. 조회 API

`Assets/02.Scripts/Domain/Localization/Loc.cs`. **전부 동기다.**
제작 화면(`CraftingUI`)은 열려 있는 동안 **매 프레임** 목록을 다시 그린다 —
async가 하나라도 끼면 그 자리는 한 프레임 비었다가 채워진다.

```csharp
using Survive.Localization;

Loc.T("UI", "craft_empty")            // 현재 로케일
Loc.T("Item", "mushroom_wood.name")
Loc.F("UI", "ingredient_entry", name, held, need)   // 값 자리 채우기 (1~3개 + params)
```

### 폴백 사슬 (세 단)

1. 현재 로케일 표
2. 기본 로케일(`ko`) 표
3. **키 자체**

**어느 단계에서도 빈 문자열이나 예외를 내지 않는다.**
번역이 빠졌다고 화면이 비면 무엇이 빠졌는지조차 보이지 않는다.
키가 그대로 뜨면 적어도 어디를 고쳐야 하는지가 보인다.
`Loc.F`도 마찬가지다 — 3절을 보라.

### 성능 계약

- 조회는 **사전 한 번 뒤짐**이다. `Loc`이 현재 로케일 표와 기본 로케일 표의
  참조를 직접 붙들고 있어, 로케일 이름으로 사전을 한 번 더 뒤지지 않는다.
- 이름표는 `LocKey` 구조체다(`Category` + `Key` 두 참조).
  `category + "/" + key`로 이어 붙이면 매 프레임 문자열이 새로 생긴다.
- 의사 번역도 로케일을 바꾸는 순간 표를 통째로 한 번 만들어 두고,
  그 뒤로는 다른 로케일과 똑같은 사전 조회다.

### 로케일 전환

```csharp
Loc.SetLocale("en");                        // 표에 없는 이름을 줘도 막지 않는다 (전부 ko로 폴백)
Loc.SetLocale(StringCatalog.PseudoLocale);  // "pseudo"
Loc.AvailableLocales                        // 표의 로케일 + pseudo
Loc.LocaleChanged += ...                    // 로케일이 바뀌었거나 표를 새로 읽었다
```

**`LocaleChanged`를 누가 들어야 하는가.**

- **매 프레임 다시 그리는 화면**은 구독할 필요가 없다. 저절로 따라온다
  (`CraftingUI.Update` → `RefreshList`).
- **한 번 쓰고 마는 글자**는 반드시 들어야 한다. 버튼 캡션, `Awake`에서 세운 안내문 등.
  창을 닫았다 열면 바뀌어 있어서 사람 눈으로는 통과한 것처럼 보인다 —
  E2E(`E2ELocaleSwitch`)가 **창을 연 채로** 바꿔서 이 차이를 잡는다.

예: `CraftingUI.ApplyStaticText()`, `BuildMenuUI`의 `Loc.LocaleChanged += Refresh`.

## 3. 문장 규칙 — 조각으로 짓지 않는다

**이 절이 번역 층의 알맹이다.** 나머지는 이것을 지키기 위한 장치다.

### 규칙

**한 줄에 보이는 문장은 표의 한 칸에 통째로 들어간다.**
그 안에서 `{0} {1} {2}`가 값이 들어갈 자리를 표시하고,
**번역가는 그 자리 순서를 마음대로 바꿀 수 있다.**

**인자로 넘길 수 있는 것은 값뿐이다.**

| 넘겨도 되는 것 | 넘기면 안 되는 것 |
|---|---|
| 숫자 (`held`, `need.count`) | 세는 단위 (`"개"`, `"마리"`) |
| 데이터에서 온 이름 (`item.displayName`) | 조사·접미사 (`"을"`, `"째"`) |
| 서식된 값 (`CraftTimeText.Short(s)`, `progress.ToString("P0")`) | 구분자 (`", "`, `"  ·  "`) |
| 다른 문장을 이어 붙인 목록 (아래 "되풀이") | 이음말 (`"그리고"`, `"남은"`) |

옳은 꼴:

```csv
UI,ingredient_entry,{0} {1}/{2},{1}/{2} {0},{0}=재료 이름 {1}=가진 수 {2}=드는 수
UI,recipe_line,{0}  ·  {1}  ·  {2},{0}  ·  {1}  ·  {2},{0}=제작물 이름 {1}=재료 목록 {2}=걸리는 시간
```

```csharp
Loc.F("UI", "recipe_line", NameOf(r), ingredients, time)
```

틀린 꼴 (이 라운드 전의 코드가 이랬다):

```csharp
sb.Append($"{need.item.displayName} {held}/{need.count * want}");   // 어순이 코드에 박혔다
sb.Append(", ");                                                     // 구분자를 코드에 박았다
sb.Append("  ").Append(Loc.T("UI", "queue_full"));                   // 조각을 이어 붙였다
```

### 왜인가

조각을 이어 붙이면 번역가가 어순을 못 바꾼다.
한국어 "가진 수/드는 수"가 영어에서 같은 순서일 이유가 없고,
세는 단위는 언어마다 아예 없거나(영어) 명사마다 다르다(한국어 개/마리/자루).

표에 실제로 그렇게 넣어 두었다 — `ingredient_entry`의 `ko`는 `{0} {1}/{2}`,
`en`은 `{1}/{2} {0}`이다. 코드는 한 줄도 다르지 않다.
(`LocWordOrderTests`가 이것을 못 박는다.)

### 유일한 예외 — 되풀이 목록

재료가 세 종이면 같은 꼴이 세 번 반복된다.
이건 조각 조립이 아니라 **되풀이**라서 통짜로 만들 수 없다. 그러므로 이것만 허용한다.

| 무엇 | 키 |
|---|---|
| 항목 하나의 틀 | `UI/ingredient_entry`, `UI/ingredient_need` |
| 항목 사이 구분자 | `UI/list_separator` |
| 그 목록을 품는 바깥 문장 | `UI/recipe_line`, `UI/buildable_line`, `UI/research_line` … |

구분자를 코드에 `", "`로 박지 않는 이유는 **중국어·일본어가 `、`를 쓰기 때문**이다.

> **이 예외를 넓혀 읽지 마라.** "구분자도 조각이니 이것도 되겠지" 하고 말 조각을
> 인자로 넘기기 시작하면 규칙이 무너진다. 되풀이에서 이어 붙이는 것은
> **전부 표에서 나온 것**이어야 하고, 코드에 적은 말은 하나도 없어야 한다.
> 경계는 이 한 줄이다 — `Loc.F`의 값 자리에 문자열 리터럴이 보이면 그것은 위반이다.

### `Loc.F`의 계약 (`LocFormat`)

`Assets/02.Scripts/Domain/Localization/LocFormat.cs`. `string.Format`을 쓰지 않는다.

- 자리표는 `{0}`부터 **0에서 시작해 빠짐없이** 이어진다.
- **순서를 마음대로 바꿀 수 있다.** `{1} {0}`도, 같은 자리를 두 번 쓰는 `{0}과 {0}`도 된다.
- 중괄호 자체는 `{{` `}}`로 겹쳐 쓴다. `{이름}`처럼 숫자가 아닌 것은 그냥 글자다.
- **절대 예외를 던지지 않는다.** 인자가 모자라도 남아도 중괄호 짝이 안 맞아도 마찬가지다.
  번역가의 오타로 게임이 죽으면 안 된다.
- 인자가 모자라면 그 자리표를 **글자 그대로 남긴다.** 화면에 `{2}`가 보이면 어디가
  고장 났는지 바로 보인다 — 빈칸으로 지우면 아무도 모른다. 잡는 것은 게이트다.

`string.Format`이 아닌 이유가 셋 있다. ① 예외를 안 던진다 ②
자리표를 채우는 그 순간 값을 알고 있어야 조사를 정할 수 있다(4절)
③ 게이트가 `LocFormat.Indices`로 자리표를 세어 호출부와 대조한다.

## 4. 한국어 조사

`Assets/02.Scripts/Domain/Localization/KoreanParticles.cs`.

### 표에는 자연스럽게 적는다

```
표   : {0}을 만들려면 {1}이 {2}개 필요합니다.
화면 : 스크랩을(를) 만들려면 도끼이(가) 3개 필요합니다.
```

**표시자를 배울 필요가 없다.** `{0}을`이라고 적든 `{0}를`이라고 적든 결과는 같다.
짝은 여섯이다.

| 표에 적는 것 | 화면에 나가는 것 |
|---|---|
| `을` 또는 `를` | `을(를)` |
| `이` 또는 `가` | `이(가)` |
| `은` 또는 `는` | `은(는)` |
| `와` 또는 `과` | `와(과)` |
| `으로` 또는 `로` | `으로(로)` |
| `아` 또는 `야` | `아(야)` |

**두 꼴을 나란히 적는 것은 사용자 결정이다** ("보통 이(가) 을(를) 해야지").
한국어 소프트웨어의 오랜 통례이고, 무엇보다 절대 틀리지 않는다.

### 어디까지 건드리는가 — 이 모듈의 진짜 위험

**자리표 바로 뒤에 붙은 조사만** 편다. 두 조건을 함께 만족해야 한다.

1. 조사 글자가 **`{n}` 바로 뒤**에 있다
2. 그 조사 **다음**이 공백·문장부호·문자열 끝이다

둘째 조건이 없으면 평범한 글이 망가진다.

| 입력 | 결과 | 왜 |
|---|---|---|
| `이 세계에서 유일하게 타는 것이다` | 그대로 | 자리표가 없다 |
| `{0}이라고 부른다` | 그대로 | `이` 뒤에 `라`가 이어진다 |
| `{0}은하계` | 그대로 | `은` 뒤에 `하`가 이어진다 |
| `{0}로서` | 그대로 | `로` 뒤에 `서`가 이어진다 |
| `{0} 이 좋다` | 그대로 | 자리표 바로 뒤가 아니다 |
| `{0}을 만든다` | `…을(를) 만든다` | 조사다 |

`으로`는 두 글자라 먼저 본다 — `로`를 먼저 잡으면 앞의 `으`가 남는다.

**한국어 로케일에서만 돈다.** `en` 문장에는 아예 해석기를 넘기지 않는다.
판정은 로케일 이름이 아니라 **값이 어느 표에서 나왔는가**로 한다 —
`en` 표에 없는 키는 `ko`로 폴백하고, 그 문장에는 조사가 붙어 있다.

### 나중에 받침으로 하나만 고르려면

**이것은 미정이 아니라 정해진 다음 단계다** ("나중엔 둘 중 잘 골라서 나올 수 있도록").

고칠 곳은 **`KoreanParticles.BothFormsResolver.Resolve` 몸통 하나**다.
그날 호출부는 한 글자도 바뀌지 않는다 — 그래서 오늘부터 그 함수가
`precedingValue`(자리표에 방금 들어간 값)를 **쓰지 않으면서도 받아 둔다.**

> **치환 전에 틀의 `{0}을`을 `{0}을(를)`로 미리 바꿔 두는 방식이 아니다.**
> 그렇게 하면 모듈이 값을 영영 못 보고, 그날 구조를 통째로 뜯어야 한다.
> 반대로 **이미 채워진 결과 문자열**에 처리를 돌리는 것도 안 된다 —
> 어디까지가 값이었는지 알 수 없고, 값 자체가 "이"로 끝나면(고사리) 오작동한다.
> `LocFormat`이 자리표를 채우면서 **그 자리에서** 부른다.

그날 필요한 규칙까지 미리 조사해 두었다. 다시 찾지 마라.

- 종성 = `(코드 - 0xAC00) % 28`, 0이면 받침 없음
- **`으로/로`는 예외** — 받침이 **ㄹ**(종성 8)이면 "로"를 쓴다 (칼로, 물로)
- **숫자로 끝나면 읽는 소리를 따른다** — 1·3·6·7·8·0은 받침 있음, 2·4·5·9는 없음
- 라틴 문자·기호로 끝나면 정답이 없다. 두 꼴 나란히로 물러서는 것이 안전하다

`KoreanParticleTests`가 "손대면 안 되는 것들"을 못 박고 있으니,
바꾼 뒤에도 그 표가 초록이면 평범한 글은 무사한 것이다.

## 6. 의사 번역 (pseudo)

`Loc.SetLocale("pseudo")` → 모든 문자열이 `[!! 최대~ !!]` 꼴로 나온다.

목적 둘.

1. **번역 밖에 있는 글자가 드러난다.** 화면에 부풀지 않은 한국어가 보이면
   그 자리는 `Loc`을 거치지 않는 하드코딩이다.
   214곳을 옮기는 동안 "다 옮겼는가"를 눈으로 판정할 수 있는 유일한 방법이다.
2. **길어졌을 때 판이 깨지는지 미리 본다.** 영어·독일어는 한국어보다 길다.
   통례대로 35% 늘린다.

`pseudo`는 CSV에 열로 두지 않는다(두면 진실이 둘이 된다 — 표에 `pseudo` 열이 있으면
파서가 문제로 적는다). 기본 로케일(`ko`) 값을 바탕으로 만들어 낸다.
표에 아예 없는 키는 부풀리지 않고 키를 그대로 낸다 —
"부풀지 않은 것이 하드코딩"이라는 신호를 흐리지 않기 위해서다.

### 글자를 고른 근거 (중요)

본문 글꼴은 `Assets/07.Fonts/TMP/ChosunGu SDF.asset`이고 **아틀라스가 Dynamic**이다.
즉 원본 `ChosunGu.TTF`에 있는 글자만 찍히고, 없으면 두부(□)가 뜬다.

**확인 방법** — `uloop execute-dynamic-code`로 아래를 돌린다.

```csharp
var font = AssetDatabase.LoadAssetAtPath<TMP_FontAsset>("Assets/07.Fonts/TMP/ChosunGu SDF.asset");
// 세 번째 인자 tryAddCharacter=true 이면 원본 TTF까지 뒤져 판정한다
bool ok = font.HasCharacter('~', false, true);
```

실측 결과(2026-08-06):

| 있다 | 없다 (□로 뜬다) |
|---|---|
| `[ ] ! ~ < > ( ) * # + = - _ / \| : . , · … ¡ ¿ ß Ł` | `— (em dash)` `− (U+2212)` `« » ‹ ›` `⟦ ⟧` `À É Ü Ž Đ` |
| `《 》 【 】 〔 〕 （ ）` `→ ← ↑ ↓ ★ ☆ ● ○ ■ ▲ ▼` | |

**악센트 라틴 문자를 쓸 수 없다** — 흔한 의사 번역 관례가 여기서는 통하지 않는다.
그래서 ASCII `[ ] ! ~`만 쓴다.
EditMode 테스트(`의사_번역은_글꼴에_있는_글자만_쓴다`)가 접두·접미가 ASCII임을 못 박고,
`표의_값에_글꼴에_없는_글자가_없다`가 CSV 값에 위 "없다" 목록이 섞이는 것을 막는다.

> 화면에 나가는 문자열에 **em dash(—)를 쓰지 마라.** 코드 주석과 이 문서에는 써도 된다.

이것이 없으면 정규식이 조용히 망가진 게이트도 통과한다.

**한글 리터럴 검사 범위.** 목록으로 관리한다 — `ScreenScopes`에 경로를 더할 때마다

목록에 남는 것을 막는다 — 목록은 줄기만 한다.

**검증 하네스는 화면이 아니다.** `Assets/02.Scripts/Testing/`은 규칙 1·3에서 뺀다.
E2E는 `Loc.T(...)`의 결과를 검사하면서 그 옆에 한국어로 **검사 이름**을 적는다.
콘솔에 나가는 글이고 번역할 것이 아니다. 여기까지 규칙을 밀면 하네스가
자기가 무엇을 검사하는지 말하지 못하게 되고, 그러면 게이트를 끄는 쪽이 편해진다.

**서식 지정자는 지역 변수로 뺀다.** `progress.ToString("P0")`을 인자 자리에 그대로 두면
`"P0"`이 리터럴로 걸린다. 그것이 서식 지정자인지 말인지 정적 분석으로는 가릴 수 없고,
가리려 들면 규칙에 구멍이 난다. 한 줄 위에서 지역 변수에 담아 넘긴다.

### 사각지대 (게이트가 검사할 수 없는 것)

`검사할_수_없는_자리를_세어_남긴다`가 매번 콘솔에 수를 적는다.
**모르는 것을 아는 게이트가 낫다.**

- **변수로 만든 이름표** — `Loc.T("Item", id + ".name")`. 어떤 키를 부르는지 알 수 없다.
- **배열로 넘긴 인자** — `Loc.F(cat, key, new object[]{…})`. 개수를 셀 수 없다.
- **리플렉션·간접 호출** — 애초에 긁히지 않는다.
- **범위 밖 파일** — `UI/`·`Domain/UI/` 밖의 한글 리터럴은 아무도 안 본다.
- **표에 있는 말이 옳은가** — 오타·잘못된 번역은 기계가 못 잡는다. 사람이 본다.

### 누락 키 게이트

`Assets/02.Scripts` 아래 모든 `.cs`를 긁어(`LocSourceScanner`) `Loc.T("Cat","key")` /
`Loc.F("Cat","key",…)`를 뽑고 CSV와 대조한다.

- **코드가 부르는 키가 표에 없으면 실패한다.** 실패 메시지에 없는 키를 그대로 적어 준다.
- 주석 안의 예시(`/// Loc.T("UI","예시")`)는 세지 않는다 — 주석을 먼저 지운다.
- **리터럴 인자만 검사할 수 있다.** `Loc.T("Item", id + ".name")`처럼 변수로 만든 키는
  판정 불가이고, 개수만 세어 콘솔에 남긴다. 그런 자리가 늘면 게이트의 사각지대가 넓어진다.
- 반대 방향(표에 있는데 코드가 안 부르는 키)은 **경고로만** 남긴다 —
  데이터 에셋 경로에서 쓰일 키는 코드에 리터럴로 나타나지 않는다.

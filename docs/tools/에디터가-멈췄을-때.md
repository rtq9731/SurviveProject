# 에디터가 멈췄을 때 — 진단과 처방

Unity 에디터가 uloop 요청에 답하지 않을 때 무엇부터 볼 것인가.

2026-08-06 하루에만 네 번 겪었고 원인이 매번 달랐다. **원인을 가르지 않고 재기동부터 하면
멀쩡한 작업을 잃는다** — 실제로 그렇게 미커밋 작업을 날린 적이 있다.

---

## 증상은 하나, 원인은 넷

`uloop`가 `Request timed out after 180000ms`를 내고, 프로세스를 보면 **살아 있고
`Responding=True`다.** 겉보기가 같아서 구별이 안 된다. 아래 순서로 가른다.

| # | 원인 | 어떻게 아는가 | 처방 |
|---|---|---|---|
| 1 | **모달 창** | `tools/unstick-unity.ps1` 이 창을 찾아낸다 | 단추를 눌러 푼다 (아래) |
| 2 | **대형 리임포트** | `Logs/AssetImportWorker*.log` 가 계속 자란다. CPU가 돈다 | **기다린다.** 에셋을 많이 지우거나 씬을 크게 고친 직후라면 몇 분 걸린다 |
| 3 | **컴파일 중** | `compile` 이 `"Compilation is already in progress"` 를 돌려준다 | 기다렸다 다시 부른다 |
| 4 | **uLoopMCP 브리지 사망** | 위 셋이 전부 아니고, 어떤 요청도(가벼운 `execute-dynamic-code` 조차) 답이 없다 | **재기동.** 그 전에 `git status` 로 잃을 것이 있는지 반드시 확인한다 |

**1번부터 순서대로 본다.** 1번은 1초면 판정되고 되돌릴 것이 없다. 4번은 마지막이다.

---

## 1. 모달 창 — `tools/unstick-unity.ps1`

### 왜 이것이 멈춤으로 보이는가

uloop는 에디터의 **메인 스레드**에 일을 시킨다. 모달 대화상자가 떠 있으면 메인 스레드가
그 창의 메시지 루프에 붙들려 있어 요청이 큐에만 쌓이고 처리되지 않는다. 창은 에디터
안쪽에 떠 있어 원격에서는 보이지도 않는다.

가장 흔한 것은 **씬 저장 확인 창**이다. 재생 모드를 오가면 씬이 dirty로 잡히고, 그 상태에서
테스트를 돌리거나 씬을 열려 하면 뜬다.

### 쓰는 법

```powershell
# 무엇이 떠 있는지 보기만 한다 (안전. 아무것도 누르지 않는다)
powershell -NoProfile -ExecutionPolicy Bypass -File tools/unstick-unity.ps1

# 눌러서 푼다
powershell -NoProfile -ExecutionPolicy Bypass -File tools/unstick-unity.ps1 -Click

# 특정 클론만
... -File tools/unstick-unity.ps1 -Click -ProjectPath "E:\SurviveProjectClones\A"

# 단추를 지정 (기본값으로 안 풀릴 때)
... -File tools/unstick-unity.ps1 -Click -Button "Don't Save"

# 창이 뜰 때까지 기다렸다 누른다 (재생 모드 진입 같은 것을 걸어 두고)
... -File tools/unstick-unity.ps1 -Click -WaitSeconds 20
```

### 안전 장치

- **기본값은 "보기만"이다.** `-Click` 을 주지 않으면 아무것도 누르지 않는다
- 기본으로 누르는 단추는 **버리는 쪽**이다 — `Don't Save` → `Discard` → `No` → `Cancel` → `OK` 순서로 찾는다
- 이 저장소의 규율이 **"에이전트는 씬을 저장하지 않는다"**이므로 그 기본값이 맞다.
  `Save` 를 누르려면 `-Button "Save"` 로 **명시해야** 한다

### 원리

Win32 `EnumWindows` 로 Unity 프로세스에 속한 보이는 창 중 클래스가 `#32770`(표준
대화상자)인 것을 찾고, `EnumChildWindows` 로 그 안의 `Button` 자식들을 훑어 글자를 맞춘
뒤 `BM_CLICK` 을 보낸다. 마우스를 움직이지 않으므로 사람이 다른 일을 하고 있어도 안전하다.

가속키 표시(`Don't &Save`)는 비교 전에 떼어 낸다.

---

## 2. 같은 창이 자꾸 뜬다면 — 원인을 없애라

누르는 것은 대증요법이다. 씬이 dirty인 상태가 반복되면 **디스크에서 다시 읽어 버리는** 편이 낫다.

```csharp
// tools 로 쓰는 .csx — execute-dynamic-code --code-file 로 부른다
using UnityEditor.SceneManagement;
var s = EditorSceneManager.GetActiveScene();
string path = s.path;
EditorSceneManager.OpenScene(path);
return "reopened: " + path;
```

이러면 미저장 변경이 버려지고 창이 뜰 이유 자체가 사라진다.

> **주의**: 이것은 **클론에서만** 쓴다. 사람이 쓰는 메인 에디터의 미저장 씬을 말없이 버리면
> 남의 작업을 지우는 것이다. 메인에서 필요하면 사람에게 먼저 묻는다.

## 3. 재기동 — 마지막 수단

**먼저 잃을 것이 있는지 본다.**

```bash
git -C <클론경로> status --porcelain
```

미커밋 작업이 있으면 **먼저 커밋해라.** WIP 커밋이라도 남기는 편이 낫다 —
2026-08-06에 에이전트 하나가 커밋 없이 한도에 걸려 작업이 통째로 날아갔다.

```powershell
Stop-Process -Id <pid> -Force
# Temp/UnityLockfile 이 남으면 다음 기동이 막힌다. 지운다.
# 그 뒤 에디터를 다시 띄운다
```

재기동 뒤 첫 리임포트가 몇 분 걸린다. 그동안 uloop는 다시 타임아웃한다 — **2번 원인**이므로
기다리는 것이 맞다.

---

## 4. 예방

- **재생 모드는 껐다 켠다.** 시나리오를 이어 돌리면 앞 시나리오의 상태가 남아 다음 것이 깨진다.
  그리고 `control-play-mode --action play` 는 비동기라 `isPlaying` 이 설 때까지 기다린 뒤
  다음 명령을 보내야 한다
- **`compile` 과 E2E를 한 명령에 묶지 않는다**
- **테스트 전에 씬을 깨끗이 한다.** dirty면 테스트 실행 자체가 거부되고, 그 거부가 모달로
  뜨면 1번 원인이 된다
